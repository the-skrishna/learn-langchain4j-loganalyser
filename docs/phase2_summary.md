# Phase 2 Summary — LangChain4j Core & Clean Architecture

## What Changed

### New Files
| File | Purpose |
|------|---------|
| `config/LangChain4jConfig.java` | Spring `@Configuration` with `ChatLanguageModel` bean and `LogAnalysisAI` bean |
| `ai/LogAnalysisAI.java` | AI Service interface — the core Phase 2 concept |

### Modified Files
| File | What Changed |
|------|-------------|
| `service/LogAnalysisService.java` | Removed: `ObjectMapper`, `@Value apiKey`, `buildModel()`, all prompt strings, all JSON parsing. Now delegates to `LogAnalysisAI`. Went from 162 → 68 lines. |
| `controller/LogAnalysisController.java` | Removed: `route()` method, `ErrorDetectionResponse` import. Service now returns correct types directly. |

### Removed Code (and why)
- `buildModel(double temperature)` — replaced by a single shared `ChatLanguageModel` bean
- `String.formatted()` prompt construction — replaced by `@UserMessage` annotations with `{{variables}}`
- `ObjectMapper` + manual JSON parsing — LangChain4j auto-deserializes based on return type
- `replaceAll("(?s)```json\\s*|```", "")` hack — no longer needed; LangChain4j instructs the LLM to return clean JSON

                      → [constructs prompt strings manually]
                      → [calls model.generate()]

                              ↓

## Concepts to Learn from Phase 2

### Day 4: ChatLanguageModel & Configuration

1. **ChatLanguageModel interface** — LangChain4j's provider-agnostic abstraction. Your code depends on the interface, not `OpenAiChatModel` directly. This means you can swap to Anthropic, Ollama, or any other provider by changing only the config bean.

2. **Single bean vs per-call model creation** — Phase 1 created a new `OpenAiChatModel` on every request. Phase 2 creates one shared instance as a Spring bean. This is more efficient and centralizes configuration.

3. **PromptTemplate** — LangChain4j's `PromptTemplate.from("...{{variable}}...")` replaces `String.formatted()`. The `{{variable}}` syntax is Mustache-style. In practice, AI Services (Day 5) handle this for you via annotations.

### Day 5: AI Services (the key concept)

4. **Interface-driven AI** — You define a Java interface, annotate methods with `@SystemMessage` and `@UserMessage`, and LangChain4j generates the implementation via `AiServices.create()`. This is the same pattern as Spring Data JPA repositories — you declare intent, the framework handles execution.

5. **@SystemMessage** — Sets the LLM's persona/role. Sent as a system message in the chat API. Think of it as "who the AI should be" for this method.

6. **@UserMessage** — The prompt template. Uses `{{variableName}}` placeholders that bind to method parameters via `@V("variableName")`.

7. **@V annotation** — Binds a method parameter to a template variable. `@V("logContent") String logContent` means the `logContent` parameter fills `{{logContent}}` in the template.

8. **AiServices.create()** — Creates a dynamic proxy that implements your interface. Under the hood, each method call: constructs the prompt → calls the LLM → parses the response into your return type.

### Day 6: Structured Output & Error Handling

9. **Return type = output schema** — When your AI Service method returns `ErrorDetectionResponse` instead of `String`, LangChain4j automatically:
   - Adds JSON schema instructions to the prompt
   - Tells the LLM to respond in JSON matching your Java type
   - Deserializes the response into your object
   - No `ObjectMapper` needed

10. **Records as output types** — Java records (`ErrorDetectionResponse`, `RootCauseResponse`) work perfectly as structured output types. LangChain4j inspects their fields to build the JSON schema.

11. **Error handling for LLM responses** — LLMs can return malformed JSON. Wrapping AI Service calls in try-catch provides graceful degradation. In production, you'd add retry logic here (covered in Phase 6).

## Key Takeaways

- **Less code, more power**: Service went from 162 lines of manual plumbing to 68 lines of clean delegation
- **Separation of concerns**: Prompts live in the AI interface, business logic lives in the service, config lives in the config class
- **Type safety**: Structured outputs give you compile-time types instead of raw strings
- **Provider independence**: Swapping LLM providers requires changing only `LangChain4jConfig`
